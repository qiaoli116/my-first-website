Git & GitHub, visually

Git is the most popular version control system — free, open source, and the thing every cloud platform like GitHub or GitLab is built around. Here's the mental model: what a repository actually is, how branches and merges work, how your machine talks to a server, and how a team shares all of it without stepping on each other.

1. Your local repository

A repository is just a folder Git is keeping a history of. Every commit is a saved snapshot; a branch is a separate line of snapshots you can work on without touching anything else.

Running git init creates the very first commit — the root of everything that follows. From there, every git commit adds a new snapshot on top of the last one. That's already version control: a timeline of versions you can always come back to.

A branch lets you split off from that timeline to try something without disturbing it. If it works out, you merge it back in — folding those commits into the branch you started from. If it doesn't, you just abandon the branch and nothing else is affected.

The exploration branch is thrown away conceptually the moment it merges back — it existed just to try something safely. The dev branch follows the same pattern: branch off production, commit freely, merge back only once it's tested.

2. Syncing with a remote — GitHub

Git itself doesn't need a server — but a cloud platform like GitHub or GitLab hosts a copy of your repository so it can be backed up, shared, and worked on from anywhere.

The repository on GitHub has the exact same shape as the one on your machine — same commits, same branches. Two commands keep them in sync:

  • clone / fetch — pull the server's history down to your machine
  • push — send your local commits up to the server

Both histories end up identical after a sync — GitHub is just another copy of the same repository, reachable over the network instead of sitting on your disk.

Tools you'll actually use

Four things cover almost everything above.

  • GitHub accountWhere your remote repositories live, and how a team shares one.
  • GitHub DesktopA visual way to commit, branch, and push/fetch without memorizing commands. The command-line git does the same thing.
  • An IDE — Visual Studio CodeWhere you actually edit the files; most editors have Git built in or via extension.
  • A local AI coding agentTools like Claude Code sit on top of all three — they can write the code, then run the git commands to branch, commit, and push it, chaining the whole workflow together instead of you doing it step by step.

3. Working as a team

A team shares one remote repository. Everyone follows the same branch → commit → merge pattern from part 1 — just against a repo other people are also pushing to.

Each person clones the shared repo, creates their own branch for whatever they're working on, commits to it freely, then merges it back in once it's ready — usually through a pull request so someone else can review the change before it lands.

Same shape as the local branch/merge diagram — just repeated once per person, all against the same shared history on GitHub.

⚠ What can go wrong

  • Merge conflicts — two people edit the same lines; Git can't guess which version wins.
  • Someone pushes straight to main/production and breaks it for everyone.
  • A branch sits unmerged for so long it drifts far from main, making the eventual merge painful.

✓ Good practice

  • Always branch off before making changes — never commit directly to main/production.
  • Open a pull request and get a review before merging.
  • Run tests before merging, and merge often so branches don't drift.

Quick glossary

The handful of terms everything above is built from.

Repository
A folder plus its full commit history.
Commit
A saved snapshot of the project at a point in time.
Branch
An independent line of commits, split off to work without affecting others.
Merge
Folding one branch's commits back into another.
Remote
A copy of the repository hosted elsewhere — e.g. on GitHub.
Clone
Download a full copy of a remote repository for the first time.
Fetch
Pull down the latest history from the remote.
Push
Send your local commits up to the remote.
